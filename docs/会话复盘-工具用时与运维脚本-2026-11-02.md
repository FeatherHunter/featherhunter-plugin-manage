# 会话复盘：工具用时、环境异常与运维脚本（2026-11-02）

复盘对象：本会话（26 轮 / 2,799 步 / 工具累计 400.6 分钟），目标是从第一性原理找出“不需要改 DSH、不影响正常会话”的环境问题，把重复且易错的操作变成脚本，并如实汇报 deck 工具故障。

## 结论

- 工具时间的 65% 花在等待（wait_agent 189.3 分钟 + job_output 70.3 分钟），不是执行；这是最大的可优化项。
- 128 次工具调用失败里，绝大多数可归为四类：长任务的超时/中断、路径与票号猜测、并发文件读写、以及大段内联程序自身的语法错误。没有一次失败来自“操作本身不可脚本化”。
- deck 工具没有工具级异常（tool isError 全为 false），但有 5 个语义级故障/陷阱（D1–D5）会造成**静默写错票或读错票**，另有 1 个契约可用性问题（D6）。
- 已把 9 类重复操作固化成 `scripts/ops` 下的 8 个脚本 + 共享库；全部只依赖 Node 标准库，默认只读，不碰 DSH、不执行 `git push`。

## deck 工具故障与陷阱（如实汇报）

工具级：220 次 deck 调用，`isError` 全为 false；以下都是**语义级**问题，返回 ok:true 但不代表做对了。

### D1（高）无 scope 的 get/report 会静默解析到别的 effort 的同号票

- 证据：`deck_issue_get` 21 次未带 effort/feature，其中 4 次拿到别的 effort 的票：seq 4972 key 10 →「README 星图区与致谢区渲染」；seq 5916 key 09 →「README 作者作品区渲染与同步」；seq 8323 key 13 →「三份交接文档与最终验收走查」；seq 8327 key 15 →「页头三件套…」；另 4 次解析正确（seq 8008/8009/8322/8325）。`deck_issue_report` seq 429 无 scope 报 key 01，落到 base-package effort 的「包骨架与三入口契约」（结果 `data.key="1"`、url 指向 `.scratch/base-package/issues/...`），把“开始实施”记到了别的票，无任何警告。
- 影响：读错票 → 基于错误上下文做事；报错票 → 处理记录丢到无关票。两者都不可见。
- 规避：任何 get/patch/report 都显式带 `effort=` 或 `feature=`；读回后核对标题与 url；本地复核用 `tickets.mjs`。
- 建议工具修：无 scope 时返回歧义错误（列出候选 effort），或强制二选一；结果里回显解析所用 scope。

### D2（中）patch 同时 progress+comment 时 text 步骤假失败

- 证据：48 次 patch 中 `text:failed` 8 次，全部带 progress（5 次 comment+close：seq 757/1329/2241/3198/3650；3 次只 progress：seq 7401/7403/7405）。reason 逐字：“进度写进去了，但进度区以外的正文跟写前对不上：这次可能顺手动到了别的区块，别当成已经写好，先读一次复核。”doc reason=`backend-unsupported`。实际进度区已写入，返回的 ticket body 含新进度。
- 影响：界面显示「这次点了 N 步，成了 N-1 步」，代理会误以为写失败而重复写。
- 规避：progress 存在时忽略 text:failed，用 `tickets.mjs` 读回确认。
- 建议工具修：progress 写入不应被当成 text 变更；items 里把 text 标为 skipped。

### D3（中）close+comment 时 comment 首行是 H1 会改写票标题

- 证据：seq 24739 patch key 00，comment 首行 `# 规格收尾核对：…`，close:true → 结果 ticket.title 变成该 H1，而正文 frontmatter `DSH-TITLE` 仍是原名；seq 24773 用 title 参数才改回。带 H2 的 close 不触发（如 seq 3198 key 04 标题不变）。
- 影响：票列表里标题被评论污染，按标题检索失效。
- 规避：关闭评论首行用 `##` 而不是 `#`；关闭后检查标题。
- 建议工具修：关闭时永不从评论推导标题，或直接拒绝 H1 评论。

### D4（低）key 归一化不一致

- 证据：`deck_issue_report` 结果 `data.key` 把 "01"→"1"、"00"→"0"（seq 429、24789），而 get/list 保留 "01"/"00"。叠加 D1 后很难发现报错票。
- 规避/建议：按数字比较 key；工具回显原始 key。

### D5（中）spec 容器票用 effort 参数读会得到误导性 `map.md not-found`

- 证据：seq 17070 key 0、17072 key 00、24358 key 00 带 effort → `map.md not-found`；seq 24764 用 feature 成功读回。create 用 effort 时报错文字稍好（“父票 00 读不到（后端原话：map.md not-found）：这张票没建”）。
- 影响：以为票不存在或目录损坏，实际是参数选错。
- 规避：spec/实施票用 `feature=`；`effort=` 只给 wayfinder map。
- 建议工具修：not-found 文案提示“spec 票请用 feature”。

### D6（信息，不是故障）list 的 `text` 只是摘要，明细在 `data.issues`

- `deck_issue_list` 返回对象含 `text`（摘要行）与 `data.issues`（完整行：total/returned/truncated/key/title/state/type/labels/url）。会话里曾因只打印 `.text` 误判“工具不返回明细”。
- 规避：读 `data.issues`。契约可用性问题，建议 text 带前 N 行或在文档里明示 data 结构。

## 工具经济与信息访问候选

- wait_agent 是最大时间坑：70 次 189.3 分钟、52 次超时。多数等待发生在“队员还在跑但本轮没有可做的事”。候选：只在真正被阻塞时 wait；并行期间推进独立工作；用更长的 job 输出收集替代短轮询。
- job_output 100 次 70.3 分钟，其中 35 次 wait:true 共请求 9,340 秒；同一个 npm test job 被反复取 4–5 次。候选：一次 wait + 结束后 `gate-summary` 读日志，而不是反复拉尾段。
- read 1,205 次 6.82 MB，热点文件集中（`orchestration/batch.ts` 38 次、`cli/main.ts` 25 次、spec.md 21 次、README 21 次）。候选：在 AGENTS.md 加一条**导航指针**（改动 rmv 前先读 DESIGN.md §10/§11 + ADR-0002，票面流程读 AGENTS-USAGE §3），减少来回探索。
- 会话日志解压不可用 Node 一次完成（zstd 多 frame）；本次用 python `zstandard` 解压。候选：把该解压命令记进排查文档，不要每次重新试错。
- 102 条 Error 结果里 27 条是内联程序语法/API 错误（Expected ',', got ...、require is not defined 等），来自超长内联程序；候选：多步操作先落脚本，run_code 只做编排。

## 仍值得做的自动化检查（候选，未在本轮实施）

1. **base 仓缺 CI 门禁**：`.github/workflows/publish-base.yml` 只在手动发布时跑 build/publish，push/PR 不跑 typecheck/vitest/docs:check。建议加 `ci.yml`（npm ci → typecheck → vitest → docs:check → build），这是现成的 check 没接线，不是新发明。
2. **源码 NUL/二进制混入扫描**：E6 的 NUL 字节让 read 直接判 binary。可在 CI 加一条扫描（源码树出现 `\0` 即失败）。
3. **deck scope 门禁**：本会话的 D1 无法在仓库内修，但可在团队流程里加“get/report 必须带 effort/feature，结果回显标题/url 需人工核对”的 checklist；写票脚本化后（tickets.mjs 只读）至少读侧可独立复核。
4. **matt 合并后重生成**：`generated.ts` 与 `tests/gate-map.json` 两次因合并变旧导致全链失败。`matt-verify.mjs` 已把这两步变成预检；建议接到 `npm test` 之前或 pre-push hook。
5. **发布传播延迟**：`base-release.mjs` 已吸收；建议 CI 发布路径也做同样的“下载 tarball 校验”步骤，而不是只看 `npm publish` 退出码。
