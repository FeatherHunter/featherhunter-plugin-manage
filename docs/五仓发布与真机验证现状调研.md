### 3.2 缺口

1. **机制覆盖率 1/5。** 只有 deck 有清单票与预检。其余四仓 `git grep "真机验证|real-machine|release-preflight|release-postflight|release-checklist"` 零有效命中（palette 那 1 处在研究笔记里）。
2. **协议是复制式同步，不是共享库。** 四个非 deck 仓的 `publish-token.ps1` 各自维护，deck 在 `:35` 写明「TOKEN-PROTOCOL v3，改动本协议时五仓同步，行首标记对齐」；而闸门代码故意做成「本仓有 `scripts/release-preflight.mts` 才生效」（deck `:158-160`）。结论：往别仓搬必须**连脚本带文档一起搬**，不能只搬调用行，否则会打印 `CHECK 跳过` 而误以为已生效。
3. **建票规范无载体。** 四仓都没有 `docs/agents/checklist-issue-template.md`，也没有 `triage-labels.md` 的「清单票不打标签」豁免条款；照搬前需各自补一份，否则清单票会被必备标签规则或 triage 筛选污染。
4. **人工对账那一半在四仓无落点。** deck 规则用 CHANGELOG「对应提交」对账（`real-machine-verification.md:106`）；palette 无 CHANGELOG（只有 `release-notes-<版本>.md`），im-companion／dsh-prompt 的 CHANGELOG 是 Keep-a-Changelog 子集（无提交号），ilife 无根 CHANGELOG。这四仓要落地得先定发行说明的写法。
5. **ilife 的粒度与版本来源都不适配。** 版本手工改、两组锁步（0.3.55／0.3.85），一次发 7 包（`release.ps1`）或 16 包（`publish-chain.mjs`）。清单票模板假定「一版一票、版本号单一」，在 ilife 要么按组开票，要么按整链快照开票，需先拍板；另外 ilife 自述屏蔽 CI（`AGENTS.md:89`），CI 侧闸门不可用，只能挂在 `tooling/*` 里。
6. **无 publishConfig／发版目录不一。** 五个仓的发布目录分别是 `package/`（deck、palette）、仓根（im-companion、dsh-prompt）、`packages/*`（ilife）。闸门脚本若按 deck 那样读「仓根 package.json 版本」，在 deck／palette／ilife 上都会读错（deck 根=待发版本恰巧一致，palette 根=开发壳，ilife 根=0.0.0）。**这是移植时最容易踩的一条**：版本号必须由发布脚本显式传参（deck 的两条路径都是这么做的：`wizard-release.sh:253` 传 `--version "$VER_NUM"`）。
7. **`gh` 依赖与认证面。** 闸门用 `spawnSync("gh", …)` 且要求 gh 已登录（deck `lib/release-checklist.mts:73-87`）；deck 的发布环境已具备（gh 2.97.0，token 含 repo scope），但 palette／im-companion／dsh-prompt 的发布脚本目前**完全不碰 gh**（不发 GitHub Release 的仓尤其），引入闸门等于给发布链新增一个外部依赖与失败面，需要 2 号退出码分支（环境问题）单独处理。
8. **palette 根目录手滑风险（与闸门无关但同域）。** 根 `package.json` 未标 `private`，发布脚本靠 `Push-Location package/` 规避；若将来在根跑 `npm publish` 会直接发开发壳。

### 3.3 一句话结论

deck 已经把「规则＋模板＋两道脚本＋两个挂载点」跑通并有一个在建实例（#1628，50%）；其余四仓**没有任何等价机制**，可挂点是现成的（每个仓的 `publish-token.ps1` 都有一段 `GATE` 紧挨着 `npm publish`），真正的工作量在补 4 份规则文档、决定各仓版本号来源与发票粒度、以及给 ilife 的「多包一次发」定票粒度。
