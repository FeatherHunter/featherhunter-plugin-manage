# 03 · CI 与发布：让五仓的 README 自动跟上最新群码

本文件给五仓维护者（以及本仓的发布者）一条可独立执行的路径：**不新增 workflow**，只在各仓已有的定时 workflow 里加一步 `readme:sync`，让限时群码每 7 天自动换成最新图。发布侧则是本仓的一条 `npm run release`。

前置事实（来自规格与已完成的实现）：

- 数据唯一真源是本仓 `contact/`（`groups.json` + `plugins.json` + 源图 + `crops.json`）；构建产物是发布包里的 `data/manifest.json` + `data/img/`。
- 客户端（弹窗）在运行时按「unpkg @latest → npmmirror /latest → jsDelivr @latest」拉清单，30 分钟缓存；README 里的图片是 **jsDelivr 精确版本**地址（可长缓存），两者解耦。
- 五仓钉**精确版本**依赖（如 `"dsh-featherhunter-plugin-base": "0.0.1"`），README 图片地址也写精确版本；数据更新走 `@latest`，不需要五仓改代码。
- 同步器只替换标记之间的内容：`<!-- CONTACT-START/END -->`、`<!-- STAR-HISTORY-START/END -->`、`<!-- THANKS-TABLE-*-START/END -->`、`<!-- MORE-START/END -->`。首次接入先跑 `readme:init` 插标记，之后只用 `readme:sync`。

---

## 1. 主路径：手动一条命令同步五仓

在五仓的父目录（目录名必须与仓名一致）执行：

```bash
npx -y dsh-featherhunter-plugin-base@latest readme:sync --all --repos <五仓父目录>
```

- `--all` 表示处理内置的 11 个 README 目标（deck ×3、palette ×3、im ×2、prompt ×2、ilife ×1）。
- 每个文件打印一行摘要（路径 + 本次替换的块）；任何文件失败**不会**留下半成品（临时文件 + 原子替换），命令退出码非零。
- 只校验不写：把 `readme:sync` 换成 `readme:sync --check`，有漂移/缺标记/脏行/标记错误就非零退出，可直接当 CI 门禁。
- 单仓调试用 `--root <仓目录>`（可重复），不带 `--all`。

首次接入（一次性）：

```bash
npx -y dsh-featherhunter-plugin-base@latest readme:init --all --repos <五仓父目录>
git -C <仓> diff          # 人工确认插入位置
npx -y dsh-featherhunter-plugin-base@latest readme:sync --check --all --repos <五仓父目录>
```

`readme:init` 幂等：已有标记的文件不会被重复插入。若 README 有可疑结构（合并冲突残留、标记配对错误），init 会**停手并报错**，不会猜测。先按报错修掉可疑行再重跑。

## 2. 次路径：挂进各仓已有的定时 workflow（不新增 workflow）

原则：**不新增 workflow 文件**，只在已有的 `thanks.yml` / `star-history.yml` 里加一步。原因是限时群码的闭环就是「有人定时跑一次 sync」，而复用已有 cron 成本最低。

在已有 job 的 `steps` 末尾追加（示例，按各仓实际 Node 版本调整）：

```yaml
      - name: Sync README contact block
        run: npx -y dsh-featherhunter-plugin-base@latest readme:sync --all --repos .
        env:
          # 五仓父目录布局不同时用绝对路径；单仓用 --root .
          NODE_OPTIONS: ""
```

要点：

- 这一步必须在 checkout 之后、提交步骤之前；如果该 workflow 原本有「提交并 push if changed」的步骤，它会自动把 README 变更提交掉。
- `npx -y ...@latest` 每次都会解析最新版本；如果 CI 环境不允许外网，改成钉版本号（`@0.0.1`）并把更新数据的工作交给本仓的 release 流程。
- 已有 workflow 的 `permissions` 需要 `contents: write`（thanks/star-history workflow 通常已经有）。
- `concurrency` 保持原样；两个 workflow 同时改 README 时，sync 的原子写 + `--check` 会保证不互相踩。

### ilife 特例

ilife 目前只有 `ci.yml`（没有 schedule）。按规格二选一：

1. 在 `ci.yml` 里加 `schedule: cron: "17 3 * * *"` 和上面的 sync 步骤（推荐，闭环完整）；
2. 不加 schedule，退化为「随发版更新」：本仓每次发版后由发布者手动跑一次 `readme:sync --all`，并接受最长一个发布周期的滞后。选择这条时在 ilife README 的 MORE 块保留「建设中」标识（`readme:sync` 会自动渲染）。

## 3. doctor：一条命令回答「哪里没跟上」

```bash
npx -y dsh-featherhunter-plugin-base@latest doctor --repos <五仓父目录>
```

默认只查本包自身（版本、数据新鲜度、远端清单可达性）。带 `--repos` 时逐仓追加检查：

| 检查项 | 含义 | 失败时怎么办 |
| --- | --- | --- |
| `package-version` | 本包 package.json 版本可解析 | 修版本号 |
| `data-freshness` | `data/manifest.json` 与 `contact/` 源数据一致 | 跑 `npm run build:data` |
| `remote-manifest` | CDN 上的清单可达且版本正确 | 等 CDN 生效或检查网络/代理 |
| `readme-blocks` | 11 个 README 的块与当前清单一致 | 跑 `readme:sync --all` |
| `readme-images` | README 里的图片地址版本 == 当前版本 | 跑 `readme:sync --all` |
| `dependency-version` | 五仓 package.json 的依赖是精确版本且等于当前版本 | 改依赖后重跑 sync |
| `inline-bundle-version` | 内联了 client 产物的仓（deck/palette）横幅版本 == 当前版本 | 重新内联并提交 |
| `cron-mounts` | 各仓 workflow 里挂了 `readme:sync`（ilife 还要求 schedule） | 按本文件第 2 节挂上 |

输出是每行 `ok|fail  <name>  <detail>`，`--json` 输出单行 JSON（`{ok, checks:[{name, ok, detail}]}`），退出码 0/1，适合直接进 CI。`--offline` 跳过网络检查（记为 skipped）。

## 4. 发布侧：本仓维护者的周更流程

```bash
# 1) 换码（源图放好后）：直接写进 contact/ 源数据
npm run contact:update -- <新微信码路径> --group wechat

# 2) 一条命令发布（含数据校验、版本推进、门禁、打包、发布、CDN 等待、五仓同步）
npm run release -- --version <x.y.z> --repos <五仓父目录>

#    也可以把换码并进发布：先 contact:update，再继续后面的步骤
npm run release -- --version <x.y.z> --image <新微信码路径> --group wechat --repos <五仓父目录>
```

`contact:update` 的退出码 3 表示「数据已写入，等人工扫码确认」，先拿真机扫一遍再发布（`--confirmed` 用于确认后重跑）。

`npm run release` 依次执行（任何一步失败都会停）：

1. `preflight`：读版本、要求 git 工作树干净；
2. `contact`：给了 `--image` 时跑 `contact:update --confirmed --no-build`（`--dry-run` 时只校验不写）；
3. `data`：`build:data` + `data:check`；
4. `version`：`npm version <patch> --no-git-tag-version`（同时改 `package-lock.json`）；
5. `typecheck` / `test` / `build`；
6. `pack`：`npm pack --json`；
7. `publish`：`npm publish <tgz> --tag latest`；
8. `registry`：轮询 `npm view` 直到新版本可见（记录生效耗时）；
9. `jsdelivr` / `unpkg` / `npmmirror`：轮询清单，jsDelivr 是必需通道，另外两个 best-effort；
10. `readme`：`readme:sync --all --repos`，再 `--check`，打印 11 个文件里被改写的图片地址数；
11. 报告写到 `.tmp/release-<version>.json`。

常用开关：`--image <png>` / `--group <id>`（换码并发布）、`--dry-run`（只校验数据 + 类型，不写任何东西）、`--skip-tests`、`--skip-publish`（本地打包演练）、`--bump minor|major`、`--version x.y.z`、`--tag <dist-tag>`（演练用 `drill`，不要动 `latest`）。

**回滚语义**：发布前失败 → 自动 `git checkout` 恢复版本/数据/README 改动（所以要求开工前工作树干净）；发布后失败 → `rollback: "manual"`，npm 版本不可变，人工决定 `npm deprecate` 或发下一个 patch。

演练记录（2026-10-31）：0.0.1 首次发布，npm 可见约 1.5 分钟（staged publishing 审核），jsDelivr `@latest` 约 2m07s、unpkg `@latest` 约 5m14s（dist-tag 缓存滞后）。换码演练用 `0.0.2-drill`（`--tag drill`，`@latest` 保持 0.0.1），真实客户端打开弹窗后 154ms 内从内置基线切换到新图，文案从「已过期」变为「11 月 6 日前有效」。三通道清单、精确版本图片响应头、README 地址改写（10/11 文件，im 根 README 因冲突残留按设计拒绝）与 HUMAN-GATE 清单见 `docs/base包-发布演练记录.md`。

## 5. 常见失败与回退

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `readme:sync --check` 报 drift | README 与当前清单不一致（多半是别人手改了块内内容） | 跑一次 `readme:sync --all`，人工看 diff 后提交 |
| 报 `markers missing` | 该文件还没跑过 `readme:init` | 跑 `readme:init --all --repos <目录>` 再 sync |
| 报 `suspicious merge-conflict residue` | README 里有 `>>>>>>> origin/master` 之类残留 | 先修掉残留行（sync 不会替你猜结构），再重跑 |
| 报 `unpaired/duplicate end-before-start` | 标记被手工改坏 | 按报错行修标记，或从 git 恢复该 README 后重新 init |
| npmmirror 通道 403 `not allow to unpkg files` | cnpm 的 unpkg 白名单政策，非本包问题 | 客户端会自动回退到 jsDelivr；需要 npmmirror 通道时向 cnpm/unpkg-white-list 提 PR 加白名单 |
| unpkg `@latest` 短时间 404 | unpkg 的 dist-tag 缓存滞后 | 等几分钟重试；发布脚本已内置轮询 |
| `dependency-version` 失败 | 五仓依赖版本落后 | 改五仓 package.json 到当前精确版本，重跑 sync |
| `inline-bundle-version` 失败 | deck/palette 内联的 client 产物是旧版本 | 用当前包重新内联产物并提交（见 01 文档） |
| `cron-mounts` 失败 | workflow 里没挂 sync（ilife 还差 schedule） | 按第 2 节挂上；ilife 也可选择「随发版」退化路径并接受滞后 |
| release 报 `working tree is dirty` | 有未提交改动 | 先 commit/stash；这是为了让自动回滚安全 |
| 发布后客户端还显示旧图 | 客户端 30 分钟模块缓存，或 CDN 未生效 | 等缓存过期/重开弹窗；用 `doctor` 的 `remote-manifest` 确认 CDN 版本 |

## 6. 验收清单（发布相关）

- [ ] `readme:sync --check --all --repos <父目录>` 对 11 个文件退出码 0；
- [ ] `doctor --repos <父目录>` 全绿（或只剩需要 HUMAN-GATE 的项）；
- [ ] 至少一个仓的定时 workflow 在真实 GitHub Actions 上跑通过一次 sync 并自动提交；
- [ ] 大陆网络（无代理）下客户端能回退到可用 CDN，弹窗显示基线或最新群码（HUMAN-GATE）；
- [ ] 真实构建链（deck/palette 的 tsc + esbuild）吃下内联产物，浏览器打开设置页无报错（HUMAN-GATE）；
- [ ] GitHub 上 README 四块观感符合规格（图片 260 宽、表格三列、标题居中）（HUMAN-GATE）。
