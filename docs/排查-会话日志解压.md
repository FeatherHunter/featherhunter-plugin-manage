# 排查：会话日志解压（多帧 zstd）

**症状**：用 Node 解压会话日志（`session.v4.jsonl.zstd`）后只有开头一小段，行数远少于实际，看起来像日志被截断或损坏。

**结论**：日志没坏。会话日志是**多帧 zstd**——每写完一批就追加一个独立压缩帧，整份文件是多个帧首尾相接；而 Node 内置的 zstd 解压只解第一帧，而且不报错。要拿全量内容，必须逐帧解，或用支持跨帧的解压库：Python `zstandard` 的 `read_across_frames=True`。

本文命令只依赖 Python 3.9+ 与 `zstandard`（缺了就 `python -m pip install zstandard`），在 PowerShell 7 与 bash 里都能直接粘贴执行。

## 为什么会「只解出第一帧」

- zstd 帧以 4 字节魔数 `28 B5 2F FD` 开头。一个 `.zstd` / `.zst` 文件里可以有任意多个帧首尾相接，解压器默认一次只处理一帧。
- DSH 按写入批次追加压缩帧，所以会话日志通常由成千上万个帧组成；帧边界与行边界没有关系，一帧可能停在一行中间。
- Node 内置的 `zlib.zstdDecompressSync()` 与 `zlib.createZstdDecompress()` 只返回第一帧，**不抛错**：解出来的正是第一批写入的记录，末行时间明显早于会话结束。
- 因此「解压出来很少」不是文件损坏的证据：先数帧，再换跨帧解压。

一次实测（Node 24、30 MB 的会话日志）：内置解压只得到 218 字节、1 行；跨帧解压得到 12,314 帧、约 120 MB、28,401 行。差距全部来自被跳过的帧。

## 解压命令（复制即用）

推荐写法：由 Python 直接写输出文件，不经 shell 重定向，PowerShell 与 bash 行为一致。

```powershell
python -c "import sys,zstandard; d=zstandard.ZstdDecompressor(); open(sys.argv[2],'wb').write(d.stream_reader(open(sys.argv[1],'rb'), read_across_frames=True).read())" ./session.v4.jsonl.zstd ./session.v4.jsonl
```

等价的 stdout 写法（bash 与 PowerShell 7 可用；**Windows PowerShell 5.1 的 `>` 会把原生命令输出重建成 UTF-16LE**，别在 5.1 里用这条）：

```bash
python -c "import sys,zstandard; d=zstandard.ZstdDecompressor(); sys.stdout.buffer.write(d.stream_reader(open(sys.argv[1],'rb'), read_across_frames=True).read())" ./session.v4.jsonl.zstd > ./session.v4.jsonl
```

要点：

- `read_across_frames=True` 是跨帧的关键；去掉它，`stream_reader` 在第一帧结束就停，和 Node 一样。
- 输入后缀是 `.zstd` 还是 `.zst` 只影响文件名，不影响解压。
- 输出固定用 `.jsonl`（每行一条 JSON），后续统计工具都按行读。
- 会话日志在 `$env:USERPROFILE\.dsh\sessions\<工作区目录>\<会话目录>\session.v4.jsonl.zstd`（bash 里把 `$env:USERPROFILE` 换成 `$HOME`），把它换成命令的第一个参数即可。

## 验证解压完整

三步一起看，任何一步不对都说明输出不完整。

1. 数帧（原始文件里的帧魔数个数）：

```powershell
python -c "import sys; b=open(sys.argv[1],'rb').read(); print('frames:', b.count(bytes.fromhex('28b52ffd')))" ./session.v4.jsonl.zstd
```

2. 数行（解压出来的 `.jsonl`）：

```powershell
python -c "import sys; print('lines:', sum(1 for _ in open(sys.argv[1], encoding='utf-8')))" ./session.v4.jsonl
```

3. 首行与末行都必须是完整 JSON（末行不合法说明输出停在半行）：

```powershell
python -c "import json,sys; ls=open(sys.argv[1],encoding='utf-8').read().splitlines(); json.loads(ls[0]); json.loads(ls[-1]); print('first/last json ok, lines:', len(ls))" ./session.v4.jsonl
```

**权威核对：逐帧解压，看解压器实际消费了几帧。** 上面三步只能证明「输出都是完整 JSON 行」，证明不了「最后一帧没被丢掉」（见下一节的尾部半帧）。把下面整段粘进 PowerShell 7 或 bash，最后一个参数是日志路径：

```powershell
python -c "import sys, zstandard
CHUNK = 64 * 1024
d = zstandard.ZstdDecompressor()
data = open(sys.argv[1], 'rb').read()
pos = frames = lines = 0
while pos < len(data):
    start = pos
    obj = d.decompressobj()
    out = b''
    while not obj.eof:
        end = min(pos + CHUNK, len(data))
        out += obj.decompress(data[pos:end])
        pos = end
        if pos >= len(data) and not obj.eof:
            break
    if not obj.eof:
        print('incomplete trailing frame at byte', start, '| complete frames', frames); sys.exit(1)
    pos -= len(obj.unused_data)
    frames += 1
    lines += out.count(b'\n')
print('frames', frames, '| lines', lines)" ./session.v4.jsonl.zstd
```

输出 `frames N | lines M`：`N` 应等于第 1 步数到的帧数，`M` 应等于第 2 步的行数；若末帧被截断，命令会打印 `incomplete trailing frame` 并以 1 退出。

说明：第 1 步按魔数计数是近似值（压缩数据里偶然出现同样四字节会多算），差一两个不影响判断；第 4 步是解压器自己走一遍帧边界，帧数才是准的。

## 常见坑

| 坑 | 现象 | 处置 |
| --- | --- | --- |
| 分帧写入 | 帧边界与行边界无关，一帧可能停在一行中间 | 先把所有帧按字节拼起来再按行切；不要逐帧按行解析 |
| Node 内置解压 | 只有第一批记录、没有报错 | 换本文的 `read_across_frames=True` 命令 |
| 尾部半帧（文件被截断） | 解压命令 **exit 0**、末行仍是合法 JSON，但最后一帧整帧丢失 | 跑第 4 步逐帧核对；`incomplete trailing frame` 即命中 |
| 尾部垃圾字节 | 解压报 `zstd decompress error: Unknown frame descriptor` | 文件被追加了非 zstd 内容，先确认日志是完整拷贝 |
| Windows PowerShell 5.1 重定向 | `.jsonl` 变成 UTF-16LE，按行工具读不出来 | 用推荐写法（Python 直接写文件）或 PowerShell 7 |
| 直接读 `.zstd` | `Get-Content` / `grep` 出乱码 | 先解压成 `.jsonl` 再查 |
| 大文件 | 一次性读入的内存峰值约为解压后大小 | 几十到几百 MB 的日志没问题；更大时按帧分块写出 |

## 解压后常用的核对口径

数字按自己的日志替换，不要当基线：

- 轮数 / 步数：`turn/end` 与 `tool/call` 等事件的计数。
- 工具耗时：按工具名汇总 `dispatch` 的耗时字段。
- 失败：`tool/call` 结果里的错误标记。

## 边界

- 本文不含真实凭据与个人绝对路径；示例一律用相对路径或环境变量。
- 解压只读日志，不写 DSH 会话目录；输出文件由你自己指定位置。
