# 证据义务：业界机制调研

> 一句话结论：业界把「验证通过」做成可签名、可复核、默认拒绝的声明链；证据不足应独立成态，不能塞进 fail。

## 机制清单

### M1 in-toto Statement / DSSE / 透明日志
- **解决**：把「某产物通过了某验证」写成机器可读、可签名、可被策略消费的断言。
- **绑定**：Statement 的 `subject[].digest` 必填（锁字节）、`predicateType` 标识谓词类型、`predicate` 放证据与结论；由执行步骤的 functionary/构建方签发，DSSE 对 `PAE(payloadType, payload)` 签名；Rekor 把签名元数据记入不可篡改日志并提供 inclusion proof。[S1][S2][S3][S6]
- **强制点**：消费方策略引擎在部署/发布前校验（in-toto-verify、admission controller 等）。
- **防凑数**：签名者身份与产物摘要分开校验；透明日志让「事后补一份声明」留下可查痕迹。
- **代价**：要维护 predicate schema、签名身份与日志可用性；keyless 依赖 OIDC/Fulcio。
- **迁移**：base 已有候选包摘要 + `evidence.json`，可直接映射 subject=候选包摘要、predicate=证据包；先做 DSSE 签名，透明日志可后置。

### M2 SLSA provenance
- **解决**：回答「这个产物由谁、用什么源码和参数构建」，而不是「测试过没有」。
- **绑定**：`predicateType=https://slsa.dev/provenance/v1`；subject 是产物摘要；`buildDefinition` 记录 external/internal parameters 与 resolvedDependencies，`runDetails.builder.id` 记录构建者。[S4]
- **强制点**：`slsa-verifier` 在 CI/发布前校验 builder 身份在可信列表、provenance 签名有效、buildType 与 externalParameters 符合预期。[S5]
- **防凑数**：验证的是「构建者身份 + 参数」，不是「存在一份 provenance」；伪造需要伪造签名。
- **代价**：需要受控构建平台与可信 builder 列表；本地构建难给出强保证。
- **迁移**：base 的「实例 + buildCommit + 候选包摘要」相当于 buildDefinition；可借用「验证者必须核对 builder 身份与参数」的纪律，防止「有 attestation 就放行」。

### M3 TAP 13
- **解决**：极小、流式、人类可读的测试结果协议，本地与 CI 都能消费。
- **绑定**：`ok/not ok N desc` 行 + `1..N` plan；`# TODO` 表示预期失败，`# SKIP reason` 表示跳过；测试行后的 `---`…`...` YAML 块是附件式诊断数据。[S8]
- **强制点**：harness 解析 TAP，按失败计数/退出码判定；`Bail out!` 中止整轮。
- **防凑数**：SKIP 必须带理由、TODO 是显式的「已知未完成」，不能把失败伪装成通过。
- **代价**：无签名、无产物摘要，证据要另存；解析器实现有差异。
- **迁移**：base 可借用三态语义（尤其「跳过必须写理由」），但 TAP 本身不适合当证据容器。

### M4 JUnit XML
- **解决**：JUnit/Ant 生态的事实标准报告，CI 普遍消费。
- **绑定**：`testsuite/testcase` 的 name/classname/time，`failure/error/skipped(message)`，`properties` 放环境信息，`system-out/system-err` 放日志；XSD 元素只有 testsuite(s)/properties/property/testcase/skipped/error/failure/system-out/system-err，**没有** hash/digest/attachment 元素。[S9]
- **强制点**：CI 的 JUnit 插件汇总结果；发布脚本读报告。
- **防凑数**：协议层几乎没有；只能靠 CI 日志留存与外部校验。
- **代价**：schema 松散，扩展靠约定；附件只能塞 `system-out` 或另存 artifact。
- **迁移**：base 若输出 JUnit 给 CI，应只当「结果摘要」；证据仍放 `evidence.json` + 归档，避免 JUnit 成为唯一证据源。

### M5 SARIF 2.1.0
- **解决**：静态分析结果的标准化交换，带结果分类、证据引用与抑制记录。
- **绑定**：`runs[].tool.driver` 标识工具；`results[].kind` 六值（notApplicable/pass/fail/review/open/informational，默认 fail）；`artifacts[].hashes` 用摘要绑定被分析文件；`result.attachments` 引证据；`invocations[].executionSuccessful` 记录执行是否成功；`suppressions[].status/justification` 记录抑制理由。[S10]
- **强制点**：代码扫描上传/合并门禁按 kind/level 判定。
- **防凑数**：kind 不是二值；抑制必须留 status 与 justification；artifact hashes 防止「报告与文件不对应」。
- **代价**：面向静态分析，不是通用测试证据模型；规则/结果结构重。
- **迁移**：base 可借用「非二值 kind + 抑制理由 + artifact hash」三件事，把 `evidence.json` 的判定从 boolean 升级为枚举。

### M6 in-toto Layout
- **解决**：把「谁在哪个步骤产出什么、产物该长什么样」写成可执行策略。
- **绑定**：layout 定义 steps（expected materials/products、functionary 公钥）、inspections（对最终产物跑命令）、artifact rules；验证时校验 layout 签名与有效期、link 元数据签名，再按 artifact rules 过滤材料/产物。[S7]
- **强制点**：client 在消费最终产物前跑 `in-toto-verify`。
- **防凑数**：阈值签名、step 公钥白名单、inspection 直接检验产物而非相信自报。
- **代价**：layout 与密钥管理复杂，对本地/动态场景偏重。
- **迁移**：base 可取其「最小内核」：每个 check 声明所需证据类型与产物摘要，验证器按规则重算；不必引入完整 layout。

### M7 OPA/Rego
- **解决**：把「证据是否满足要求」写成可版本化、可单测的策略。
- **绑定**：input 为 attestation/evidence JSON；规则输出 allow/deny 与 reason；规则体全不成立时结果是 `undefined`，需要显式 `default` 兜底。[S11]
- **强制点**：CI step、admission controller、发布脚本调用 `opa eval`/SDK。
- **防凑数**：策略可要求「predicateType 必须匹配 + UI 检查必须有 screenshot + 非 UI 必须有 log/json」；策略自身用 `opa test` 覆盖坏样本。
- **代价**：Rego 学习成本；`undefined` 若当 false 处理会变成默认放行（必须 fail closed）。
- **迁移**：base 最适合把「UI 检查=截图+日志/数据，非 UI=日志/数据」写成 Rego，`default allow := false`，并用「缺证据」样本测策略。

### M8 Sigstore policy-controller
- **解决**：在 Kubernetes 准入时强制镜像签名与 attestation 策略。
- **绑定**：`ClusterImagePolicy` 的 `images` + `authorities`（key/keyless）+ `attestations[].predicateType` + CUE/Rego 策略；不匹配则拒绝 Pod 创建。[S12][S13]
- **强制点**：admission webhook，集群级、调用方无法绕过。
- **防凑数**：predicateType 精确匹配 + attestation 内容策略 + 签名者身份校验。
- **代价**：只覆盖 K8s 镜像；策略调试与密钥管理成本。
- **迁移**：base 的发布门禁可类比 admission——在 publish 脚本里做不可跳过的 verify，而不是提供一个可选命令。

### M9 CI / 发布门禁
- **解决**：把「验证通过」变成合并/发布的前置条件。
- **绑定**：分支保护要求指定 status check 通过才可合并；npm `--provenance` 把 tarball 与构建来源绑定并在 registry 展示；`gh attestation verify` 校验 artifact 与 attestation。[S14][S27][S28]
- **强制点**：分支保护/环境审批/发布脚本；registry 上的 provenance 徽章只是提示，不是闸。
- **防凑数**：required check 必须由可信 workflow 产生；attestation 校验 signer 与 source。
- **代价**：平台锁定；离线/本地要自建等价物。
- **迁移**：base 的 preflight 已在发布脚本里，可把证据策略校验并入同一 exit code 契约；关键是「不可跳过」。

### M10 突变测试（mutation testing）
- **解决**：量化测试对「人为注入缺陷」的杀伤力，即区分力。
- **绑定**：mutation score = killed / all mutations；PIT 的 `mutationThreshold` 就是「低于该分数则构建失败」。[S15][S16]
- **强制点**：构建阈值；报告逐 mutant 列 killed/survived。
- **防凑数**：突变体是自动注入的已知坏，测试必须红；等价突变体会稀释分数，需排除。[S15]
- **代价**：每个 mutant 跑一遍测试，计算贵；阈值选错会逼出无意义断言。
- **迁移**：base 的「对抗式审查矩阵」已是手工版；可升级为「每条检查配一个必须红的坏输入夹具」，把 kill 结果写进证据。

### M11 差分测试与负对照
- **解决**：没有 oracle 时，用两个实现/版本的输出差异发现缺陷；用负对照证明检查本身会红。
- **绑定**：同一输入集跑 A/B，记录差异样本与最小化用例；负对照记录「故意注入故障 → 检查必须失败」。[S18]
- **强制点**：CI 差分 job；发布前跑负对照。
- **防凑数**：差异必须可复现、可最小化；负对照必须命中预期失败点。
- **代价**：需要第二个实现或可信基线；差异分类要人。
- **迁移**：base 的「必须红」夹具就是负对照；差分可用于新旧版本行为对比，但要有稳定基线。

### M12 覆盖率
- **解决**：衡量被执行代码比例，是充分性的必要不充分条件。
- **绑定**：行/分支/MC-DC 覆盖报告；本身不绑定产物，也不说明断言质量。
- **强制点**：CI 覆盖率阈值（常见但容易误导）。
- **防凑数**：无；覆盖率可以很高而断言为空。
- **代价**：把覆盖率当有效性证明，会得到「测试很多但抓不到 bug」。
- **迁移**：base 不应以「覆盖了多少场景」作为通过依据；ICSE 2014 的结论是覆盖率与测试套件有效性相关性不强，应要求负对照/突变分数。[S17]

### M13 安全关键标准的追溯
- **解决**：在受监管场景里，证明「需求→设计→实现→测试→结果」每一步都有记录且可复核。
- **绑定**：DO-178C 以目标组织符合性，生命周期数据含需求、设计、代码、测试用例/规程/结果、配置索引与 SAS，验证结果与问题报告要留存；FAA 以 AC 20-115D 认可 DO-178C/ED-12C。[S19] ISO 26262-6 覆盖软件单元验证、集成与测试，Part 8 覆盖验证与文档管理。[S20][S21] IEC 62304 按需求/架构/详细设计/单元验证/集成/系统测试/发布分阶段留记录，FDA 2023 指南要求上市前提交软件文档。[S22][S23]
- **强制点**：审定当局/功能安全评估/独立评审；高安全等级对部分验证活动要求独立性。
- **防凑数**：双向追溯 + 评审记录 + 问题报告闭环；不是「有一份测试报告」就够。
- **代价**：文档与评审成本高，变更影响分析重。
- **迁移**：轻量版是「每条 check 声明对应哪条声称/需求 + 结果 + 评审人」；OpenFastTrace 用文本标签建立需求→实现→测试链，可作为本地可执行的追溯表。[S25]

### M14 证据不足 / 不适用的独立状态
- **解决**：区分「证据说失败」「没有足够证据」「不适用」，避免被迫二选一。
- **绑定**：SARIF `kind` 的 notApplicable/review/open 与 suppression 的 underReview+justification；[S10] TAP 的 SKIP 必须带 reason、TODO 是预期失败、`Bail out!` 是中止；[S8] JUnit `skipped message`；[S9] CycloneDX VEX 的 analysis.state 含 in_triage/not_affected，且 not_affected 应给出 justification；[S24] OPA 的 `undefined`；[S11] GSN 以 goal/strategy/solution 组织论证，未展开的目标有 undeveloped 语义（标准正文未逐字核对）。[S26]
- **强制点**：报告消费者必须按状态分别处理；门禁只能对 PASS 放行，对 INCONCLUSIVE 要求补证或人工裁决。
- **防凑数**：N/A 与 SKIP 都要求理由字段；理由为空即视为无效。
- **代价**：状态机变复杂；「未决」容易被当成拖延借口，需要时限与升级路径。
- **迁移**：base 的 verdict 建议五态 PASS/FAIL/INCONCLUSIVE/BLOCKED/N/A（附理由），归档时非 PASS 必须有 reason；这比 boolean 更诚实。

## 关键启示
1. 先锁字节再谈结论：subject 摘要/artifact hash 是证据的地基，路径和时间都不算绑定。[S2][S10]
2. 校验和只证明「与清单一致」，签名+身份+透明日志才证明「谁说的」；SHA256SUMS 不是防伪。[S3][S6]
3. 门禁要放在调用方绕不过的位置并默认拒绝；策略引擎的 `undefined` 必须当拒绝处理。[S11][S12][S14]
4. 「有测试」不等于「有区分力」：突变分数、负对照、差分才是区分力证据；覆盖率与有效性相关性弱。[S15][S17][S18]
5. 把「证据不足/不适用」做成独立状态并要求理由，否则执行者只能在 pass/fail 里撒谎。[S8][S10][S24]
6. 安全标准的可迁移内核是「需求→测试→结果→评审」的双向链与独立复核，不是文档厚度；轻量实现可用标签化追溯。[S19][S21][S25]
