## Problem Statement

base 的「真机验证」已经能把「怎么跑」标准化：声明、批次、候选、证据清单、run.json、退出码 0/1/2。但「凭什么说通过」还没有标准化：

- **空口 PASS**：`CheckResult.evidence` 可以是空数组，缺证据不影响判定；一条 custom 检查只返回 `ok: true` 就能进「通过」。消费仓可以跑出一次绿色的真机验证，却拿不出任何可复核的证据。
- **证据无关**：现有场景只把证据当成「要保留的文件路径」交给 evidence store，没有要求说清这份证据是什么、哪一步取的、看哪里、要证明什么。截一张无关页面、贴一段无关日志，同样会进证据清单。
- **有证据无推理**：报告里没有「这条检查声称了什么、反例是什么、这些证据为什么能排除反例」。评审者拿到 run.json 只能看到 ok/detail，无法判断 PASS 是否成立。
- **给不出人话**：agent 生成的验证报告容易写「正常 / 成功 / 没问题」这类不可判定的结论，人打开证据也看不懂在证明什么。

用户的需求：**使用这个能力的仓库、插件，在每一次真机验证中都必须提供证据（有界面的截图、没界面的日志或数据），并从第一性原理自证这些证据是否真的能证明声称。**

## Solution

在真机验证能力内建「证据义务」——每条检查在跑之前就声明三样东西，跑的时候由原语自动采集绑定，跑完由检查自己给出推断：

- **声称 + 反例**：这条检查断言什么；如果它是假的，哪个观测会不一样。
- **证据**：有界面 → 截图；没界面 → 日志或数据。由原语自动挂到该检查，不需要场景手工搬运路径。
- **推断**：这些证据为什么排除了那个反例（观测之后写，防止事前背答案）。

缺证据或缺自证的检查**不算通过**（记未决），整次验证的结论标「证据不全」，不输出「通过」。每次 run 自动渲染一份人读**证据卡**（Markdown），与 run.json 同源——人复核验证结果、排查失败、有争议时看它，不需要额外流程。

证据卡与机器校验遵循同一份**证据规格**：每份证据一行描述（是什么 / 哪一步取的 / 看哪里 / 要证明什么）；截图整屏带场景信息与关键标注；日志只取相关时间窗、保留原始路径与行号、敏感字段脱敏；数据给关键字段摘要 + 原始文件 sha256；描述写「看到什么」，不用「正常 / 成功 / 没问题」这类不可判定词。

## User Stories

1. 作为场景作者，我想在写检查时就声明「声称 + 反例」，以便推断不是跑完以后再编的理由。
2. 作为场景作者，我想让原语自动把截图 / 日志 / 数据挂到检查上，以便不用手工搬运证据路径。
3. 作为场景作者，我想在观测之后写一句推断，以便说清这些证据为什么排除了反例。
4. 作为场景作者，我想有界面的检查必须交截图、没界面的检查交日志或数据，以便证据形态与验证对象匹配。
5. 作为场景作者，我想缺证据时得到明确的未决状态和补采提示，以便知道下一次该补什么。
6. 作为场景作者，我想内建步骤有默认的声称 / 反例 / 推断模板，以便不用为基础设施写一遍废话。
7. 作为插件维护者，我想一次验证的结论区分「失败」与「证据不全」，以便不把证据缺失当产品缺陷。
8. 作为插件维护者，我想「证据不全」时退出码非零，以便 CI 不会把残缺的验证当绿。
9. 作为插件维护者，我想每次验证都自动产一份证据卡，以便交接、复盘、评审直接看人话。
10. 作为插件维护者，我想证据卡一检查一节，含声称、条件、步骤、观测、证据、推断、判定，以便评审不必翻 JSON。
11. 作为插件维护者，我想证据卡的证据表带路径、sha256、字节数与采集时间，以便核对原件没有被替换。
12. 作为插件维护者，我想声明在验证开始时被冻结（哈希进报告），以便运行中没法事后弱化声称。
13. 作为评审者，我想每份证据都有一行「是什么 / 哪一步取的 / 看哪里 / 要证明什么」，以便判断证据是否相关。
14. 作为评审者，我想截图带能认出场景的信息（页面标题、版本、时间）与关键处标注，以便知道这是哪一屏。
15. 作为评审者，我想日志证据保留原始文件路径与行号且敏感字段脱敏，以便回查又不泄密。
16. 作为评审者，我想数据证据给关键字段摘要 + 原始文件 sha256，以便核对「哪个值、什么条件」。
17. 作为评审者，我想描述用「看到什么」而不是「正常 / 成功」，以便我能用反例去反驳。
18. 作为评审者，我想证据卡里能看到批次、提交、包 sha256、profile、时间等条件，以便结论可定位到具体代码。
19. 作为 AI agent，我想按同一契约交证据与推断，以便 agent 生成的验证报告也能被人复核。
20. 作为 AI agent，我想缺证据时报告直接告诉我缺哪类、哪一步，以便下一轮自动补采而不是猜。
21. 作为 AI agent，我想证据卡从结构化数据渲染而不是手写，以便卡片与 run.json 永远一致。
22. 作为 base 维护者，我想义务校验是纯规则、可测试的，以便不靠人工纪律维持。
23. 作为 base 维护者，我想新增状态与字段有明确迁移说明，以便消费仓升级时不误读报告。
24. 作为新插件作者，我想只读 README / AGENTS-USAGE 就能写出合格义务与证据，以便接入不需要口头传授。
25. 作为评审者，我想未决的检查在报告里列出缺失的证据类型与自证字段，以便一次补齐。

## Implementation Decisions

**契约（脏活在契约层）**

- 场景步骤新增可选**义务声明**：可证伪声称（claim）、反例（falsifier）、必需证据类型（requiredEvidence：screenshot / log-slice / json / text / file）、运行后推断（inference）。声称与反例随检查定义在跑之前存在；推断在观测后由场景体或内建模板给出。
- 检查结果携带**义务快照**：claim / falsifier / requiredEvidence / inference / 声明时间 / 义务哈希。run 开始时冻结，运行中不得修改或补写声称，防止事后合理化。
- 检查状态新增 **inconclusive（未决）**：应通过的检查缺证据或缺自证时进入此状态，并附 missingEvidence / missingSelfProof 与补采 hint。通过（pass）必须满足义务；失败（fail）不改判（证据缺失只记缺口）；skip / blocked 沿用各自理由字段，不要求证据。
- run 状态新增 **inconclusive（证据不全）**，人话输出「证据不全」；退出码保持 0/1/2 三值：硬失败 1，受阻或未决 2，其余 0。
- 证据项扩展机器可判字段：一行描述（description，必填）、原始来源路径与行号区间（sourcePath / lineRange，日志与文件证据必填）、关键字段摘要（summary，数据证据必填）。现有 path / bytes / sha256 / capturedAt 不变；证据引用（path + sha256 + kind）不变。
- run 报告追加可选义务汇总（required / satisfied / inconclusive / advisory）与证据卡产物指针；旧读者可忽略新字段。报告 schemaVersion 保持 1，新增枚举值在变更说明中列出。
- 证据卡渲染输入只有 run 报告 + 证据清单 + 批次/身份信息；不手写，保证与机器可读报告同源。

**编排**

- 义务判定在每条检查完成后立即进行，不阻断后续步骤；--fail-fast 仍只对 fail 生效。
- 证据绑定沿用现有「原语产出路径 → 场景声明采纳 → 证据库绑定」通道；路径解析失败不再静默丢弃，而是记为义务缺口（原来的静默行变可见）。
- 证据类型由场景声明，base 不猜「有没有界面」；声明错误（把 UI 检查标成非 UI）由人复核证据卡时抓。
- 证据规格的机器可判子集：每份证据必须有非空描述；截图必须是 png 且非空；日志证据必须有来源路径与行号；数据证据必须有摘要。不可判定词（正常 / 成功 / 没问题）只记 lint 提示，不判失败——语义判断留给人。
- 证据卡每次 run 自动写入 run 目录并登记为 artifact；人话输出末尾给证据卡路径。
- 过渡机制：profile 增加 `evidencePolicy: "strict" | "advisory"`，默认 strict；advisory 仍记录未决与缺口，但不改退出码，并在报告 notes 标 advisory（仅供存量场景升级，文档写明是临时逃生舱）。
- 不新增 CLI 命令：证据义务与证据卡随 run 自动产生；不引 OPA/Rego 之类运行时，纯 TS 规则。
- 与 ADR-0002 一致：不建 createHarness，不改变 L2 原语出口；能力仍是 index.ts 导出的原语 + 既有命令。
- base 版本按契约新增（新状态、新字段）做 minor 升级，发布说明列出：新状态含义、退出码 2 的新含义、profile 新字段、场景新字段。
- 文档更新：DESIGN.md 证据链一节增「证据义务」；AGENTS-USAGE 的「先冻、再绑、再归档」与自检纪律增义务与证据规格；README 与 capability-description 同步；describe 输出列证据规格要点。

## Testing Decisions

- **好测试**：只断言外部行为——run 命令产出的 run.json 字段与状态、退出码、证据卡 Markdown 的内容、stderr 人话；不测私有校验函数与渲染内部结构。
- **测试缝（只设一个）**：`run` 命令入口（RunCommandDeps）。用 fake machine + 真实 fixture 场景文件驱动，跟现有场景测试同一层；这是消费方能看见的最高边界。声明校验错误也从这个缝进，通过分类错误断言，不另开契约解析缝。
- **先例**：现有场景测试、证据库测试、证据清单测试、报告测试；fixtures 已有 fake launch / fake capture / fake machine / 场景模块样例。
- **用例**：
  1. 义务齐全且证据自证齐全 → 检查 pass、run passed、退出 0；证据卡含六元组（声称 / 条件 / 步骤 / 观测 / 证据 / 推断）。
  2. UI 检查缺截图 → 该检查 inconclusive、run state「证据不全」、退出 2、报告列出缺的证据类型。
  3. 缺推断或推断为空 → inconclusive 并指出缺自证字段。
  4. 证据路径解析不到 → 义务缺口可见（不再静默丢证据）。
  5. 声明快照哈希出现在 run.json 与证据卡；运行中不可改。
  6. 旧场景完全没有义务声明 → 每条检查未决并给「如何声明」hint，不静默 pass。
  7. advisory 策略 → 记录未决但不改退出码，报告 notes 标 advisory。
  8. fail 检查缺证据 → 仍记 fail（不被未决吞掉），报告同时列证据缺口。
  9. 证据卡与 run.json 同源：卡片里的路径 / sha256 与报告一致。
  10. 证据规格机器校验：描述为空、日志缺行号、截图非 png 各自产生对应缺口或提示。
  11. skip / blocked 检查不要求证据，但必须带既有理由字段。

## Out of Scope

- 发布门禁、签核、review.json、策略开关（用户已明确：只管验证本身，不碰发布流程）。
- 固定命令（self-check / 单实例 / 并发 / freeze 等）所产检查的证据义务：它们的检查由 base 预置、没有消费方写的声称；按同一契约在后续票补齐。
- 机器判断推断「成不成立」：语义判定只能由人看证据卡。
- 防伪三件套（subject digest、DSSE 签名、Rekor 透明日志）：防的是「证据是谁说的」，本次只做实字节绑定 + 人工复核；日后可把 evidence.json 映射为 in-toto predicate。
- 新增退出码 3/4：保持三码，未决沿用 2。
- 真实浏览器截图的「整屏 / 巧合场景」机器校验：只校验格式与声明，观感由人判。
- 五仓接入：本仓只建设 base，五仓按发布包与各自 README / AGENTS-USAGE 自助接入。

## Further Notes

- 第一性原理：机器能判「有没有、绑没绑、改没改」，判不了「推断成不成立」。证据义务把「有没有」变成机器硬判，把「成不成立」留给人看证据卡。反例是证伪的最小单位；没有反例的自证只是「我觉得没问题」。
- 本轮用户决策（2026-11-03）：缺证据 / 缺自证的检查不算通过，整次验证标「证据不全」（D1 采纳推荐）；自证最小格式 = 一句反例 + 一句推断（D2 采纳推荐）。
- 证据规格五条来自本会话的 HTML 问卷收敛；价值判断来自业界机制调研笔记（自身摘要 + 签名 + 透明日志是防伪三件套；覆盖率与有效性弱相关；非 PASS 必须写理由）。
- 本规格是 2026-11-01 已关闭「真机验证能力」规格的增量，不重开旧规格；新增内容只覆盖证据义务与证据卡。
- 迁移风险：默认 strict 会让存量场景在没有声明义务时变「证据不全」；这是有意的钳制。过渡期用 profile 的 advisory 显式降级，文档需给出存量场景的补声明示例。
