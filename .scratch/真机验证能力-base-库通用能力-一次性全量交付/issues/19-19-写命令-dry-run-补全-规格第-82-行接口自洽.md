## 背景（规格审计发现）

规格 .scratch/真机验证能力-base-库通用能力-一次性全量交付/spec.md 第 82 行逐字要求：“全部命令支持 `--json` 与 `--dry-run`（写操作类），并共享一套「计划 → 执行 → 报告」骨架：计划是纯函数，dry-run 打印计划即真实执行的同一份结论。”

逐命令审计（packages/base/src/real-machine-verification/cli/commands/*.ts 的 `*_FLAGS`）发现：`--dry-run` 目前只有 5 条写命令实现（launch、concurrent、single-instance、cleanup、batch）。以下 8 条写命令不接受 `--dry-run`：

| 命令 | 写什么 | 现状 |
| --- | --- | --- |
| self-check | work root 下的 run.json + evidence | FLAGS 无 --dry-run |
| stop | 实例目录的 stopped.json | STOP_FLAGS 无 |
| isolation | work root 下的探针产物 | ISOLATION_FLAGS 无 |
| model --fix | profile 的 cordis.patch.yml | MODEL_FLAGS 无 |
| install | profile 的 node_modules | INSTALL_FLAGS 无 |
| freeze | out 目录的 tgz + candidate.json | FREEZE_FLAGS 无 |
| run | work root 下的 run 目录（report/evidence/logs） | RUN_FLAGS 无 |
| evidence add\|archive | evidence 文件 / 归档目录 | ADD_FLAGS / ARCHIVE_FLAGS 无 |

这使「接口是契约」不成立：文档承诺 dry-run 可看计划，实际报 unknown option。

## 要建什么

给上述 8 条命令补 `--dry-run`：

1. `--dry-run` 时**零写盘、零 spawn、零 HTTP**；stdout 只输出计划（`--json` 时恰好一段 JSON：`{ schemaVersion: 1, command, dryRun: true, plan: ... }`；人类模式逐行可读）。
2. 计划必须是**真实执行所用的同一份计划**：能抽纯函数 `planX(...)` 的抽出来，dry-run 与执行器共用同一个函数调用点（照 launch.ts:9 与 launch.ts 的 planInstance 先例）；不要为 dry-run 另写一套影子逻辑。
3. 计划内容至少包含：将写的目标路径（绝对/相对标注）、将执行的外部命令 argv、将创建/复制的对象计数、以及决定是否执行的输入（如 freeze 的 git dirty 判定、install 的 tgz 摘要、self-check 的声明路径与检查清单、stop 解析出的目标实例）。
4. 前置失败仍按现有失败语义输出（exit 1/2 与 expected/actual/hint），不要因为 dry-run 就吞掉输入错误；`--dry-run` 不得改变真实执行路径的任何行为。
5. 把 `--dry-run` 加进各命令的 `*_FLAGS` 允许集；`cleanup` 的「--dry-run 优先于 --yes」语义同理适用。
